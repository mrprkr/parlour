`apps/ios` is a client, in the same sense a satellite is a client: it records,
it posts, it plays the answer back. Everything that thinks, holds a key or
touches the house runs on the Mac at home. What the phone adds is that it is
the one you already carry, that it knows about HomeKit without asking anybody,
and that it has a small model of its own for when the house cannot be reached.

It speaks the routes in [Clients](/docs/clients) and nothing private: `/health`
to check, `/voice` for a recording, `/ask` for text. Anything you could build
against those routes, the app is built against too.

## Building it

The Xcode project is generated from `apps/ios/project.yml` rather than checked
in, because a `.pbxproj` is not a thing a person can review.

```sh
brew install xcodegen
pnpm exec nx run ios:app          # generate the project and open it
pnpm exec nx run ios:xcodebuild   # compile for the simulator
pnpm exec nx run ios:xcodetest    # run ParlourTests
```

Signing is left to you: set `PARLOUR_DEVELOPMENT_TEAM` before generating, or
pick a team in Xcode once. HomeKit and the local network both need a real
device rather than the simulator. There is no iOS job in CI yet, so the app is
built by hand.

## The four permissions

A voice assistant that will not say what it is allowed to do is not one
anybody should install, so the Settings tab lists all four with a mark against
each, and the reason in every prompt says what the permission buys you.

| Permission | What it buys | Raised by |
| --- | --- | --- |
| Microphone | Recording while the talk button is held | Holding the button |
| Local network | Finding the server with Bonjour, then talking to it | Opening the app |
| HomeKit | The rooms and accessories on the House tab | Opening that tab |
| Speech recognition | Making out a request on the phone when the server cannot be reached | Only when the on-device answer is switched on |

HomeKit and multicast are entitlements as well as prompts. Plain HTTP to the
house is allowed by `NSAllowsLocalNetworking`, which is scoped to the local
network and nothing else, because the server is on a private address and
speaks HTTP. That is the same trade the phone page makes, and the same reason
a reverse proxy is worth having if you want to reach the house from outside it.

## Finding the server

The same way a satellite does. The app browses for `_parlour._tcp`, and
because Bonjour hands back a service rather than an address, it opens a
connection to the service and reads the host and port off the resolved path.
Anything it finds is offered in Settings. An address typed in by hand wins
over anything found, and from then on that is the only server the app talks
to, for the same reason a satellite pins the first server it trusts.

Browsing is also what raises the local network prompt, so it happens as the
app opens rather than in the middle of someone trying to say something.

## The model on the phone

The app wraps Apple's Foundation Models, which need iOS 26 and Apple
Intelligence switched on. It is off by default, and it is a fallback rather
than a first stop: the phone has no tools, so it cannot switch anything on,
read a sensor or look anything up. The server is local first for a reason, and
the phone deferring to it is the same reason one step further out.

When it is on and the server cannot be reached, the recording is transcribed
on the device with on-device speech recognition and answered on the device,
and the answer is labelled as coming from the phone rather than from home.
Nothing in that path leaves the handset.

## HomeKit

The House tab reads the homes, rooms and accessories HomeKit already knows
about and can flip anything with a power state. It is deliberately not how
Parlour controls the house: the agent's tools go through Home Assistant on the
server, which is the one place that knows what is connected to what. This is
the second opinion in your pocket, and the screen that still works when the
Mac at home is switched off.
